# Publishing and recovery

Implementation preparation does not publish anything. Intended first release is `1.0.0`; main remains `1.0.0-SNAPSHOT`. All three reactor coordinates share one version under `io.github.adumeige.infermats`. This standalone parent inherits no application framework. Delivery adapts the merged [StateFlow workflow](https://github.com/adumeige/vaadin-stateflow/blob/9bfa00a22d203e74731805d9072a3cf8f99203d8/.github/workflows/ci.yml) and helper from that same revision.

## Setup

1. Verify ownership of `io.github.adumeige` in Sonatype Central Portal and generate a Portal publishing token.
2. Configure repository secrets `CENTRAL_USERNAME` and `CENTRAL_PASSWORD` with the token username/password.
3. Configure `GPG_PRIVATE_KEY` with the ASCII-armored signing private key and `GPG_PASSPHRASE` with its passphrase; publish the matching public key so signatures can be verified. The workflow maps these secrets to `MAVEN_GPG_KEY` and `MAVEN_GPG_PASSPHRASE` for Maven GPG's Bouncy Castle signer.
4. Ensure repository Actions can write packages and contents for the GitHub phase and allow the requested 90-day artifact retention. GitHub publication uses only the built-in `GITHUB_TOKEN`, with `contents: write` and `packages: write` scoped to that job. No PAT is required.
5. Merge the implementation into main, review the source commit, then dispatch **Build and publish Infermats** from main with a new explicit `major.minor.patch` version. Routine pushes and PRs only verify; do not dispatch as part of implementation acceptance.

## Local verification

Use Java 21 and the checked Maven 3.9.9 wrapper (`mvnw.cmd` on Windows). Kotlin 2.3.10, serialization 1.10.0, JUnit 5.12.2, Dokka 2.2.0, GPG 3.2.8 and Central publishing 0.11.0 are pinned and verified together. Ordinary tests need no inference API keys, signing keys or registry credentials:

```sh
./mvnw -B -ntp verify
./mvnw -B -ntp -Pcentral-release verify -Dgpg.skip=true
python3 .github/scripts/check_artifacts.py
./mvnw -B -ntp install
python3 .github/scripts/check_consumers.py
python3 -m unittest discover -s .github/scripts -p 'test_*.py' -v
```

The unsigned release profile attaches real Kotlin sources and Dokka HTML. `verify` never calls registries. Artifact checks require exactly binary/source/documentation JARs for each library and no parent JARs. The mirroring tests use a temporary local file repository, including real Maven publication and partial recovery. Tests never execute inference. Dependency resolution needs Maven repositories on a first build; this is separate from runtime library behavior.

For an intentionally authorized local deploy, put token credentials in Maven `settings.xml` under server ID `central`, supply the signing environment variables, set a release version in an isolated checkout, and use `./mvnw -B -ntp -Pcentral-release clean deploy`. Defaults are manual staging: `central.autoPublish=false`, `central.waitUntil=validated`. Inspect and publish the staged deployment in Central Portal. Only the manual CI job explicitly sets automatic publication and waits for `published`.

## Workflow sequence

A release-level concurrency lock spans both registries. Build checks run first. Central preflight checks strict release syntax, all four credentials, absence of the tag, and the exact selected source SHA. It changes all reactor POMs in the runner's isolated checkout, commits those changes locally and saves a Git source bundle plus manifest. Main's snapshot commit is not pushed or modified.

The Central job builds and signs once, then deploys the parent POM and both libraries. The signed bundle, source bundle and manifest are retained for 90 days even when publication fails or times out. The manifest distinguishes `sourceCommit` from the local `releaseCommit`, identifies the three artifacts and records bundle/payload SHA-256 hashes. If failure occurs before a bundle exists, only artifacts actually created can be retained.

The dependent GitHub job runs only after Central reports `published`. It checks manifest provenance and retained bundle bytes, restores the exact release commit, creates the annotated `v<version>` tag and a draft Release. It mirrors the retained signed POMs, library JARs, sources, documentation and signatures into GitHub Packages. The helper rejects missing/extra artifacts, invalid checksums, unsafe ZIP paths, and conflicting existing registry bytes. Identical existing files are skipped. Uploads are read back and verified before assets are attached and the Release becomes public. Asset names include the module artifact ID, so modules cannot collide.

This is sequential delivery with recovery, not an atomic transaction. A tag can be visible while the GitHub Release remains a draft. Registry metadata/checksum sidecars generated by Maven are transport data; the signed payload files mirrored from Central must match exactly. Retained source and Central bundles plus manifest are attached to the draft/public Release as well.

## Recovery

* A Central timeout has an **uncertain outcome**. Inspect the original run's Central deployment ID/log and Portal deployment status before taking any action. Do not assume the version was unpublished and dispatch again.
* If Central succeeded and GitHub failed, rerun **only the failed GitHub job from the original workflow run**. Keep the original retained artifacts. Never rebuild, re-sign or redeploy Central to recover GitHub.
* If registry files already exist identically, recovery skips them. A byte conflict fails; investigate the conflicting repository/version rather than replacing it. Do not delete or overwrite published registry files to force recovery.
* An existing tag must point to the retained release commit. An existing Release must still be a draft. A fully public Release causes this workflow to refuse replay; inspect it instead.
* If Central is verified failed before publication, investigate its validation errors. Preserve the original evidence and signed bundle; recovery of the original deployment is a Portal operation. A changed implementation requires a newly reviewed source/version, not silent replacement of an uncertain release.
* Download retained artifacts before the 90-day window ends. Once source/bundle evidence is lost, this workflow cannot safely reconstruct an already published version.

Public Kotlin API and emitted wire shape are both compatibility surfaces. Field defaults, normalization, ordering, omission and null handling can change model behavior and need documented semantic-versioned changes. New models receive separate independent modules rather than a runtime registry. JSON import, response decoding, SDK execution and prompt optimization are excluded from V1.
